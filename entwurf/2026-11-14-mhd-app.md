# MHD-App – Entwurf

Stand: 14.11.2026

## 1. Worum es geht

Ein Edeka-Markt (selbstständiger Kaufmann) möchte eine App, mit der seine
Mitarbeiter das Mindesthaltbarkeitsdatum (MHD) der Ware im Regal kontrollieren.
Vorbild ist das frühere Vorgehen bei tegut: Artikel scannen, MHD der vordersten
Ware eingeben, die App berechnet, wann der Artikel das nächste Mal geprüft werden
muss, und zeigt jeden Tag, was heute dran ist.

**Ziele, in dieser Rangfolge:**

1. **Keine abgelaufene Ware im Regal.** Ein verpasster Hinweis ist schlimmer als
   ein überflüssiger. Alles, was abgelaufen oder überfällig ist, bleibt sichtbar,
   bis jemand es erledigt.
2. **Früh reagieren:** Ware rechtzeitig reduzieren, bevor sie abläuft.

**Wer sie benutzt:** Mitarbeiter eines Marktes am Handy (oder am Handscanner mit
Browser), die Marktleitung für Einstellungen.

**Wer sie zuerst sieht:** Die IT von Edeka prüft den Code, lädt ihn herunter und
testet die App selbst am Handy, bevor sie im Markt eingesetzt wird.

## 2. Nicht-Ziele (bewusst nicht in der ersten Fassung)

- Anbindung an Kasse oder Warenwirtschaft des Marktes
- Zentrale Artikelliste von Edeka (gibt es nicht: jeder Kaufmann kauft anders
  ein, die Sortimente unterscheiden sich je Markt)
- Verwaltungsoberfläche für viele Märkte, Selbst-Registrierung neuer Märkte
- Betrieb ohne Netz (Offline), App aus einem App-Store, Push-Benachrichtigungen
- Mengen- oder Abschriftenwerte in Euro

## 3. Anti-Ziele (wäre ein Fehlschlag, auch wenn es technisch funktioniert)

- Ein abgelaufener oder überfälliger Artikel verschwindet still von der Liste.
- Ein Markt sieht Artikel, Prüfungen oder Mitarbeiter eines anderen Marktes.
- Die Kontrolle mit der App dauert länger als heute mit Papier.
- Im öffentlichen Repo stehen Zugangsdaten, interne Adressen, echte Namen
  oder echte Marktdaten.

## 4. Rahmenbedingungen

- **Öffentliches GitHub-Repo.** Edekas IT soll ohne Einladung hineinsehen,
  herunterladen und testen können. Folge: keine Geheimnisse im Code und nur
  erfundene Testdaten.
- **Demo am Handy ohne eigenen Server**, mit HTTPS (die Kamera im Browser
  funktioniert nur über HTTPS oder `localhost`).
- **Eigenständig:** eigene Datenbank, keine Verbindung zu anderen Anwendungen.
  Aufbau und Sicherheitsmuster folgen einem früheren eigenen Projekt.
- Oberfläche auf Deutsch.
- Startet mit **einem Markt**, Daten aber von Anfang an je Markt getrennt
  (jede Zeile trägt `markt_id`), damit weitere Märkte ohne Umbau dazukommen.

## 5. Erwogene Wege

| Weg | Vorteil | Nachteil | Entscheidung |
|---|---|---|---|
| **A. Statische Web-App auf GitHub Pages + Supabase** (Muster aus einem früheren eigenen Projekt) | HTTPS-Adresse fürs Handy ohne Server und Kosten; Sicherheitsmuster dort erprobt; Code öffentlich, Daten geschützt | Abhängig von einem Cloud-Dienst; ob Edekas IT das erlaubt, ist offen; kostenlose Projekte pausieren bei Inaktivität (nicht nachgeprüft) | **gewählt** |
| B. FastAPI + PostgreSQL in Docker auf gemietetem Server | Volle Kontrolle | Server mieten, einrichten, pflegen; Domain und Zertifikat nötig | verworfen: mehr Betrieb ohne Gewinn für die Demo |
| C. Eigene Android-App | Offline, schneller Scan | Neue Technik, iOS extra, Verteilung als APK | verworfen, bis fehlendes Netz sich als echtes Problem zeigt |
| D. Fertige MHD-Software kaufen | Kein Bau | Nicht geprüft; Auftraggeber will selbst bauen | zurückgestellt |

**Absicherung gegen die Abhängigkeit von Supabase:** Die gesamte Fachlogik liegt
in einer SQL-Datei (reines PostgreSQL). Verlangt Edekas IT einen eigenen Betrieb,
lässt sich Supabase selbst hosten oder durch PostgreSQL + PostgREST ersetzen; die
Oberfläche bleibt gleich. Das Supabase-Projekt wird in der EU-Region (Frankfurt)
angelegt.

## 6. Aufbau

**Muster aus einem früheren eigenen Projekt gespiegelt** (Sicherheitsprinzip,
Datenbankschema, Testgerüst). Im Code kurz vermerken, dass Aufbau und Testgerüst
von dort übernommen sind.

| Pfad | Inhalt |
|---|---|
| `docs/` | Die App als statische Seite für GitHub Pages: HTML, CSS, JavaScript-Module, ohne Framework und ohne Build-Schritt |
| `docs/config.js` | Supabase-URL und öffentlicher `anon`-Schlüssel (absichtlich öffentlich) |
| `supabase/schema.sql` | Schema `mhd`, alle Tabellen und Funktionen; idempotent (erneutes Ausführen ist unschädlich und behält Daten) |
| `supabase/demo-daten.sql` | Erfundener Demo-Markt mit Testartikeln und Demo-Mitarbeitern |
| `tests/` | Tests gegen PGlite mit nachgebildeten Supabase-Rollen, `node --test` |
| `entwurf/` | Dieser Entwurf (nicht unter `docs/`, damit er nicht als Webseite ausgeliefert wird) |
| `README.md`, `ANLEITUNG.md` | Einrichtung für die IT (Befehle für cmd.exe), Bedienung für den Markt |

**Sicherheitsprinzip (wie im früheren Projekt):**

- Alle Tabellen im Schema `mhd`; `anon` und `authenticated` haben keinen Zugriff
  auf das Schema; Row Level Security überall an, keine Policies.
- Der Browser ruft nur Funktionen `public.mhd_*` auf (`security definer`), die
  Anmeldung, Rolle und Markt auf dem Server prüfen.
- Ein Test prüft jede `public.mhd_*`-Funktion auf Rechte und Marktgrenze; neue
  Funktionen müssen dort eingetragen werden.
- Bekannte Falle: Ändern sich die Parameter einer Funktion, legt
  `create or replace` eine **zweite** Funktion an; die alte bleibt mitsamt Rechten
  aufrufbar. Alte Fassung vorher ausdrücklich mit `drop function if exists` löschen.

## 7. Anmeldung

Zweistufig:

1. **Markt-Anmeldung** über Supabase Auth (E-Mail und Passwort, ein Konto je
   Markt). Das Gerät bleibt angemeldet. Dadurch ist die App nur für den Markt
   zugänglich, und Supabase begrenzt Fehlversuche.
2. **Mitarbeiter-Auswahl mit PIN** (4–6 Ziffern) innerhalb des Marktes. Damit wird
   jede Aktion einem Mitarbeiter zugeordnet. PINs nur als Hash gespeichert
   (`pgcrypto`, `crypt`/`gen_salt('bf')`). Nach 5 falschen PINs ist der Mitarbeiter
   15 Minuten gesperrt. Nach 30 Minuten ohne Aktion muss die PIN neu eingegeben
   werden.

Rollen: **Marktleitung** (Mitarbeiter, PINs, Warengruppen und Regeln verwalten)
und **Mitarbeiter** (scannen, prüfen). Die erste Marktleitung und das
Markt-Konto werden bei der Einrichtung im SQL-Editor angelegt.

Von Mitarbeitern nur Anzeigename oder Kürzel speichern (Datensparsamkeit).

## 8. Fachlogik

**Ein MHD je Artikel:** gespeichert wird das früheste MHD, das im Regal steht
(die vorderste Ware), wie bei tegut.

**Regel je Warengruppe**, vom Markt einstellbar, mit Vorgaben beim Anlegen:

| Einstellung | Bedeutung | Beispiel-Vorgabe |
|---|---|---|
| `pruef_vorlauf_tage` | So viele Tage vor dem MHD wird der Artikel geprüft | Molkerei 3, Trockensortiment 14 |
| `reduzier_vorlauf_tage` | So viele Tage vor dem MHD soll reduziert werden; darf nicht größer sein als `pruef_vorlauf_tage` | Molkerei 2, Trockensortiment 7 |
| `max_intervall_tage` | Spätestens nach so vielen Tagen wird geprüft, auch wenn das MHD weit weg ist | 30 |

**Drei Termine je MHD** (entschieden vom Auftraggeber: drei Termine statt
täglicher Wiedervorlage, damit die Liste kurz bleibt):

1. **Prüfen** am Tag MHD − `pruef_vorlauf_tage`
2. **Reduzieren** am Tag MHD − `reduzier_vorlauf_tage`
3. **Läuft heute ab** am Tag des MHD („heute Abend rausnehmen“)

**Nächster Termin** eines Artikels, neu berechnet nach jeder Aktion am Tag *d*:
der früheste der drei Termine, der **nach** *d* liegt, spätestens aber
*d* + `max_intervall_tage` (dann als Termin „Prüfen“). Jede Aktion erledigt damit
alle Termine bis einschließlich heute. Liegt kein Termin mehr nach *d* (Aktion am
MHD-Tag oder später, MHD unverändert), gibt es keinen nächsten Termin: der Artikel
wird am Folgetag als abgelaufen rot.

**Liste „Heute“**, Abschnitte in dieser Reihenfolge; ein Artikel erscheint nur im
obersten zutreffenden:

1. 🔴 **Abgelaufen / versäumt:** MHD liegt vor heute, oder der nächste Termin
   liegt vor heute. Bleibt stehen, bis eine Aktion ihn erledigt; fällt nie von allein
   weg. Angezeigt wird, was versäumt wurde (abgelaufen seit, Prüfen/Reduzieren
   versäumt seit).
2. 🟠 **Läuft heute ab:** nächster Termin ist heute, Art „läuft heute ab“.
3. 🟠 **Heute prüfen:** nächster Termin ist heute, Art „Prüfen“.
4. 🟡 **Heute reduzieren:** nächster Termin ist heute, Art „Reduzieren“.
5. ⚪ **Ohne Bestand – wieder da?:** Artikel, die seit
   `pruef_vorlauf_tage` Tagen (mindestens 1, höchstens `max_intervall_tage`) als
   „kein Bestand“ gemeldet sind. Schutz davor, dass
   nachgelieferte Ware ohne Scan unbemerkt im Regal steht. Ein angelegter Artikel,
   dessen MHD noch nie gespeichert wurde (keine Aktion seit dem Anlegen), steht
   hier **sofort** als „MHD fehlt noch“.

„Heute“ ist das Datum in Europe/Berlin, berechnet auf dem Server.

**Aktionen** (nach Scan oder Tippen auf einen Eintrag), jede zählt als Prüfung:

- **Geprüft:** Mitarbeiter bestätigt oder ändert das vorderste MHD (kann neuer
  sein, wenn frische Ware nachgerückt ist). Ändert sich das MHD, entfällt ein
  früherer Reduziert-Vermerk.
- **Reduziert:** ein Tipp; MHD bleibt, Reduziert-Vermerk wird gesetzt.
- **Aussortiert:** abgelaufene/nicht verkaufbare Ware entfernt. Danach entweder
  neues vorderstes MHD eingeben oder „kein Bestand“ wählen.
- Im Abschnitt „Ohne Bestand“: **wieder da** (MHD eingeben), **weiter ohne
  Bestand** (Nachfrage erneut nach `pruef_vorlauf_tage` Tagen, mindestens 1, höchstens `max_intervall_tage`) oder **aus dem Sortiment
  nehmen** (Artikel ruht; ein neuer Scan holt ihn zurück).

Wird ein MHD eingegeben, das schon vor heute liegt, warnt die App sofort
(„abgelaufen – aussortieren“).

**Beispiel** (Molkerei 3/2, MHD 20.11.): erscheint am 17.11. unter „Heute prüfen“,
am 18.11. unter „Heute reduzieren“, am 20.11. unter „Läuft heute ab“. Wird am 18.11.
nichts getan, steht er ab 19.11. rot als „Reduzieren versäumt“. Wird am 20.11. nur
„geprüft“ gedrückt und die Ware bleibt, steht er am 21.11. rot als „abgelaufen“.

Jede Aktion wird mit Mitarbeiter, Zeitpunkt, altem und neuem MHD protokolliert
(nur anfügen, nie ändern). Die Marktleitung kann das Protokoll ansehen und
filtern.

## 9. Artikel und Sortiment

- Der Markt baut sein Sortiment **durch Scannen** auf: einmal einen Rundgang durch
  den Markt, danach neue Ware beim Einräumen scannen. „Nie geprüft“ heißt damit
  „nie erfasst“; das ist die bekannte Grenze (siehe Abschnitt 13).
- **Scan eines unbekannten Artikels:** Die App fragt Open Food Facts direkt aus dem
  Browser ab (`https://world.openfoodfacts.org/api/v2/product/<EAN>?fields=product_name,brands,quantity,categories_tags`;
  CORS ist erlaubt, am 14.11.2026 geprüft). Gefundene Daten werden vorgeschlagen,
  der Mitarbeiter bestätigt Name und wählt die Warengruppe. Nicht gefunden: Name von
  Hand eingeben. Gespeichert wird im Markt; Open Food Facts wird je Artikel und
  Markt nur beim ersten Scan gefragt. Fällt Open Food Facts aus, geht es mit
  Handeingabe weiter.
- Abdeckung: Open Food Facts führt für Deutschland rund 2.700 Artikel „Gut &
  Günstig“ und 4.500 „Edeka“ (Abfrage 14.11.2026). Welcher Anteil eines
  Marktsortiments das ist, ist nicht gemessen.
- **Abgewogene Ware mit Waagen-Etikett** (Fleisch, Käse, Wurst): Der Strichcode
  enthält Gewicht oder Preis und ist je Packung verschieden. Entschieden vom
  Auftraggeber: in dieser Fassung **ohne Scan**. Solche Artikel legt die
  Marktleitung von Hand an (ohne EAN), der Mitarbeiter wählt sie über eine Suche
  aus der Liste „Artikel ohne Strichcode“. Wird ein Code mit Präfix 20–29
  (marktinterne Nummern) gescannt, verweist die App auf diese Liste, statt einen
  neuen Artikel anzulegen. Spätere Stufe: Waagen-Code auswerten, sobald der Aufbau
  der Etiketten des Marktes bekannt ist.
- Optional je Artikel ein Platz (z. B. „Kühlregal 3“), damit die Liste nach Gang
  sortiert werden kann.

## 10. Scannen

- Kamera im Browser: `BarcodeDetector` wo vorhanden (Chrome auf Android), sonst
  eine mitgelieferte JavaScript-Bibliothek für EAN-8/EAN-13 (Datei im Repo, kein
  CDN, damit die IT alles prüfen kann).
- Handscanner, die als Tastatur arbeiten, funktionieren über das Eingabefeld.
- EAN von Hand eintippen ist immer möglich.
- MHD-Eingabe als Ziffernfeld `TT.MM.JJ` mit großen Tasten.

## 11. Als App auf dem Handy (Icon auf dem Startbildschirm)

Die App lässt sich auf den Startbildschirm legen und startet dann ohne
Adressleiste. Muster aus dem früheren Projekt
(`docs/manifest.webmanifest`, `docs/sw.js`, `docs/app-installieren.js`):

- `manifest.webmanifest` mit Name „MHD“, `display: standalone`, `start_url`/`scope`
  `./`, Icons 192 und 512 px; dazu `apple-touch-icon` und `theme-color` im Kopf der
  Seite.
- Knopf **„Als App installieren“**: Meldet der Browser `beforeinstallprompt`
  (Chrome/Edge auf Android), öffnet der Knopf den Installationsdialog. iPhone/iPad
  kennen das nicht: dort eine kurze Anleitung mit dem Teilen-Symbol. Läuft die App
  schon installiert, kein Hinweis.
- Service Worker nur gegen veraltete Dateien nach einem Update (eigene Dateien
  immer beim Server nachfragen); er speichert nichts und macht die App nicht
  offline-fähig.
- Strenge Content-Security-Policy; `connect-src` nur Supabase und
  `world.openfoodfacts.org`.
- Zu prüfen beim Bau: Kamera-Zugriff in der installierten App auf dem iPhone
  (nicht getestet).

## 13. Bekannte Grenzen

- Ein Artikel, der nie gescannt wurde, ist der App unbekannt. Gegenmittel in
  dieser Fassung: Rundgang beim Start, Scannen beim Einräumen. Spätere Stufe, falls die Kasse des Marktes eine Artikeldatei liefern
  kann: je Markt einspielen und „im Sortiment, nie geprüft“ anzeigen.
- Ohne Netz keine Bedienung.

## 14. Demo und Übergabe an die IT

- GitHub Pages aus `docs/`, Demo-Supabase-Projekt mit `demo-daten.sql`
  (erfundener Markt, Testartikel mit echten öffentlichen EANs aus Open Food Facts
  und erfundenen MHDs). Im README stehen nur die Zugangsdaten des **lokalen**
  Testservers. Konto, Passwort und PINs der Demo im Internet bekommt die prüfende
  IT direkt; so kann kein Fremder die Demo-Mitarbeiter sperren oder PINs
  durchprobieren. `demo-daten.sql` ist wiederholbar und
  setzt die MHDs relativ zum Tag der Ausführung, sodass jeder Abschnitt der Liste
  gefüllt ist; erneutes Ausführen setzt die Demo zurück. Nächtliches Zurücksetzen
  per `pg_cron`, falls im Supabase-Projekt verfügbar (nicht geprüft).
- README: was die App tut, Sicherheitsprinzip, eigenes Supabase-Projekt einrichten
  (Schritte, Befehle für cmd.exe), Tests starten.
- **Lokaler Testserver** (`npm start`):
  die echte Oberfläche gegen die echten SQL-Funktionen in einer eingebauten
  Datenbank, mit Demo-Daten. Damit kann die IT die App nach dem Herunterladen ohne
  Supabase-Konto vollständig ausprobieren (statt einer Vorschau mit Attrappen-Daten).
